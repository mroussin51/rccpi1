A well‑architected starter for a simple web app

Start with one VPC, public subnets for ALB and NAT, private subnets for app and database. Use an ALB to route HTTPS to containers or EC2. Store static assets on S3 with CloudFront. Centralize logs and enable budget alarms to prevent cost surprises.

Steps

  1. Create VPC with 2–3 AZs; split public/private subnets.
  2. Place ALB + NAT in public; app + DB in private.
  3. Use ACM for TLS; terminate HTTPS at ALB.
  4. Serve static assets from S3; cache via CloudFront.
  5. Ship logs/metrics to a central destination; set budgets.

Key figures

  • AZ count: 2 minimum, 3 preferred.
  • Cache hit target: 60–80% for static assets.

Pick the right compute: EC2, Lightsail, or Beanstalk

Choose Lightsail for the simplest single‑instance sites, EC2 for full control and networking, and Elastic Beanstalk for managed deploys with minimal ops. If containers are planned, prefer ECS on Fargate for zero server management and predictable scaling.

Steps

  1. Map constraints: control, scaling, ops time.
  2. If minimal ops: Lightsail/Beanstalk; need control: EC2.
  3. For containers: ECS on Fargate to avoid VM patching.
  4. Add ALB + ACM for clean HTTPS and blue/green deploys.

Key figures

  • Operational effort: Lightsail < Beanstalk < EC2.

Separate dev, test, and prod sanely

Use identical templates with smaller sizes for non‑prod. Isolate accounts or VPCs, and require role‑based access with MFA. Automate deployments from main branch to dev/test, and gated releases to prod with approvals and change logs for traceability.

Steps

  1. Use IaC to define all environments consistently.
  2. Apply least‑privilege roles; enforce MFA.
  3. Automate deploys; require approvals for prod.
  4. Mirror monitoring and alerts across envs.

Key figures

  • Drift checks: weekly in non‑prod; daily in prod.
